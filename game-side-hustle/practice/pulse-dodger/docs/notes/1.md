# 核心洞察

**游戏和后端只差一个字:「帧」。**

```
后端:  有人请求  →  算一次  →  返回  →  睡觉
                                        ↑
                                   大部分时间在这

游戏:  没人请求  →  每秒自己醒 60 次  →  每次把整个世界重算+重画
                                        ↑
                                   永远不睡
```

这**一个**差别,派生出游戏开发几乎所有特有的坑。

而你已经会的比你以为的多:分层、依赖注入、接口隔离、CI 门禁,你在 FastAPI 里天天用。游戏里真正陌生的只有三样:**帧循环、碰撞、手感**。

# 逐个拆解

## 1. 画面怎么出来的

### 最朴素的想法

屏幕是一块像素矩阵。**让东西"动"的唯一办法,是每秒擦掉重画几十次。**

游戏里没有"移动一个物体"这个操作,只有"**这一帧把它画在新位置**"。

```
第 1 帧          第 2 帧          第 3 帧
┌─────────┐     ┌─────────┐     ┌─────────┐
│ ●       │     │   ●     │     │     ●   │
└─────────┘     └─────────┘     └─────────┘
  全擦重画        全擦重画        全擦重画

每秒 60 次 → 你的眼睛以为它在滑动
```

### 这个 demo 的做法:开局前先"印"好图

```
BootScene(游戏开始前跑一次)
   │
   ├─ 用 Graphics 画三层同心圆  ┐
   │   外发光 / 中层 / 核心 / 高光点  │ 画一次
   │                            ┘
   ├─ generateTexture('tex-player')   ← 烘成一张位图存起来
   │
   └─ 之后每帧只做:把这张图贴到 (x, y)
```

**为什么不每帧现画?** 这是真踩过的坑:

```
Phaser 的 Graphics 不缓存
   ↓
每帧把所有绘制命令重新提交
   ↓
一个圆内部拆成约 100 个点,每点 new 一个对象
   ↓
46 个圆 = 每帧约 4600 次分配 = 低配设备 GC 抖动
```

改成烘贴图后:**每帧 1 次贴图绘制,几乎免费。**

> **后端类比**:每个请求现拼 HTML vs 启动时渲染好缓存。

> 🧠 **自检**:如果我把 `BootScene` 里生成贴图那几行删掉,游戏会怎样?
> <details>答:所有实体变成"找不到贴图"的绿色问号方块。因为每帧只是"贴图",图本身不存在了。</details>

## 2. 东西怎么动 —— 新手第一大坑

### 最朴素的想法

新位置 = 旧位置 + 速度 × **经过的时间**。

初学者会写成:

```ts
x = x + 5        // ❌ 每帧移动 5 像素
```

坑在于 **"每帧"不是固定时长**:

```
        帧率        每秒帧数     实际速度
    ┌─────────┬──────────────┬─────────────┐
    │  60Hz   │   60 帧/秒   │  300 px/秒  │  ← 你的屏幕
    │ 144Hz   │  144 帧/秒   │  720 px/秒  │  ← 玩家的电竞屏
    │ 165Hz   │  165 帧/秒   │  825 px/秒  │
    └─────────┴──────────────┴─────────────┘
                                    ↑
                          同一份代码,难度差 2.75 倍
```

正确写法乘上 `delta`(这一帧过了多少毫秒):

```ts
x = x + speed * delta / 1000    // ✅ 每秒移动 speed 像素,与帧率无关
```

### 谁负责补偿

```
┌──────────────────────┬────────────────┬──────────┐
│ 谁在动               │ 谁补偿         │ 你管吗   │
├──────────────────────┼────────────────┼──────────┤
│ 碎片飞行(物理)     │ 引擎自己做     │ ❌       │
│ 缩放/淡出(Tween)   │ 引擎自己做     │ ❌       │
│ 定时器               │ 引擎自己做     │ ❌       │
│ ★ 你手写的每帧插值   │ **你自己**     │ ✅ 必须  │
└──────────────────────┴────────────────┴──────────┘
```

这个 demo 里"你手写的"只有两处:球跟鼠标、充能环弧长追赶。都用这个公式:

```ts
const t = 1 - Math.pow(1 - 0.18, delta / (1000/60));
//           把"每帧靠拢 18%"换算成"每 16.667ms 靠拢 18%"
```

> **判断标准:代码里出现 `delta` 就是对的,没出现就要怀疑。**

> 🧠 **自检**:碎片的移动我没写 `delta`,为什么不出问题?
> <details>答:碎片走的是 `setVelocity()`,交给 Arcade 物理引擎,引擎内部按定步长计算。只有绕过引擎、自己改 `x`/`y` 的代码才需要你补偿。</details>

## 3. 玩家怎么介入

### 两个真实的坑

**坑一:开局球自己飞。**

```
❌ 原来:每帧读"鼠标现在在哪"
        ↓
   场景刚建时,鼠标位置 = 上个场景最后点击的位置
        ↓
   (菜单的"开始游戏"按钮位置)
        ↓
   每局开场球都先朝那儿飞一段

✅ 现在:只在"鼠标动了"时更新 followTarget
        球跟 followTarget 走
```

**坑二:手机上技能永远放不出来。**

```
鼠标:  移动 = 挪鼠标(不按)     放技能 = 按下
        └──────── 天然分开 ────────┘

触屏:  移动 = 按住拖            放技能 = 按下
        └──────── 撞车! ──────────┘
        
   玩家为了移动必须按下 → 每次移动起手都浪费一次技能
   → 充满就被下一次触摸吃掉 → 手机上根本放不出来
```

修法:**第一根手指只管移动,第二根手指才放技能**,而且球显示在手指上方(否则被手指盖住)。

> **可迁移的判断:鼠标和触屏不是"一套代码两种设备",交互语法根本不同。**

## 4. 怎么算"碰到了"

### 最朴素的想法

两个圆碰上了 ⟺ **圆心距离 < 两半径之和**。

```
        r₁              r₂
      ●─────         ─────●
      └────── d ──────────┘

      d < r₁ + r₂  →  撞上
```

就这么简单。这个 demo 全是圆,所以碰撞是最简单的形式。

### 但"擦身而过"暴露了一个深坑

demo 有个机制:贴着碎片过去但没撞上,给奖励。

天真写法是每帧算"碎片当前位置到玩家的距离":

```
第 N 帧                        第 N+1 帧
  ●                                      ●
  │                                      │
  距离 60(不在擦身带)          距离 55(不在擦身带)

  但中间这条路径 ↓ 可能正好扫过玩家!
  ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━●
              ✗ 漏判了
```

而且**帧率越高帧间隔越小、越不容易漏** —— 这本身就是帧率不一致。

修法:判定**线段**而不是点。

```
❌ 点判定:   ●  . . . . . .  ●      只看两个端点
✅ 线段判定: ●━━━━━━━━━━━━━●      看整条扫过的路径
```

> **可迁移的判断:高速物体的碰撞,判定的是"这一帧扫过的路径",不是"这一帧所在的点"。**

## 5. 怎么让玩家爽(juice)—— 后端完全没有的东西

### 最朴素的想法

**同一条游戏规则,反馈做得好不好,体感差十倍。**

规则上,吃到一个点就是 `score += 10`。但玩家应该感受到:

```
吃到点的那 0.3 秒里同时发生:

   视觉  ├─ 8 颗粒子炸开
         └─ 一个小球从能量点飞向你的充能环   ← 把"蓝点→充能"画出来
   听觉  └─ 一声清脆音,音高随连击上行
   数字  └─ 分数弹跳(1 → 1.18 → 1)
   状态  └─ 充能环的弧"甩"一下再停住(阻尼过冲)
```

那条**飞行粒子**是整个设计里最巧的一笔:它把"蓝点 → 充能"的因果关系变成一条肉眼可见的抛物线,**比任何文字提示都有效,而且不用读字、天然多语言**。

### juice 工具箱

| 手段     | 表达什么   | 用在哪                | 陷阱                              |
| -------- | ---------- | --------------------- | --------------------------------- |
| 震屏     | "重"       | 死亡、大清场          | **幅度大了看不清碎片 = 负 juice** |
| 顿帧     | "撞击"     | 死亡 140ms、清场 80ms | >150ms 玩家以为卡了               |
| 慢动作   | 给读图时间 | 死亡后 420ms          | —                                 |
| 粒子     | "炸开"     | 各处                  | 同屏要有上限                      |
| 音高上行 | "越来越好" | 连击、逐个清场        | —                                 |

震屏强度在这个 demo 里**硬性封顶 0.010**,注释写着理由:

> 在躲避游戏里,遮挡信息的 juice 是负 juice。

### 死亡序列 —— 设计最密的一段

```
t=0      顿帧(近似定格)
         碎片撞击点炸出白环 + 全屏红色闪一下
              ↓
t=140ms  解除顿帧,进入 1/3 速慢动作 + 震屏
              ↓
         ★ 除了杀死你的那个碎片,所有东西 alpha 降到 0.30
           凶手保持全亮 + 白色描边
              ↓
         屏幕上只有一个东西是亮的
         ——— 这就是"我为什么死"的全部答案
              ↓
t=560ms  恢复正常 → 复活询问 / 结算
```

> **可迁移的判断:死亡反馈的目的不是好看,是让玩家知道自己错在哪。"我死得不冤"是"再来一局"的唯一来源。**

> 🧠 **自检**:为什么吃能量点**不**加震屏?
> <details>答:一局要吃 30-60 次。高频震屏三分钟就让人晕,而且每次震动都让玩家短暂读不出碎片位置——在躲避游戏里这是直接杀人。</details>

## 6. 怎么让玩家留下

### 留存链条

```
第一局能玩明白 → 撑过 20 秒 → 死得心服口服 → 知道差多少 → 再来一局
      ↑             ↑            ↑              ↑
   首局引导     开局宽限期    死亡序列    "差 N 分破纪录"
```

### 关键设计:把"最优策略"变得有趣

这游戏原来的最优玩法是:

```
   ┌──────────────────────────────┐
   │  离所有碎片尽可能远           │
   │  顺便捡点                     │  ← 又安全又无聊
   └──────────────────────────────┘
              而无聊是留存杀手
```

加了两个机制把玩家往危险里推:

```
连击:  2.6 秒内连吃,倍率最高 ×5    → 逼你抓紧去吃下一个
擦身:  贴着碎片过 +2 分 +3 充能     → 逼你主动靠近危险
```

有个细节值得记:**得分乘倍率,充能不乘**。否则后期充能溢出,冲击波失去稀缺性 —— 这是典型的数值设计考量。

### 难度曲线长什么样(这次实读了代码)

```
        0 秒                45 秒               90 秒 ────► 之后封顶
生成间隔  900ms  ──────────────────────────────►  260ms
碎片速度  150    ──────────────────────────────►  400
每次几个  1 ─────────────┤  2 ────────────────────────────
能量点    1400ms ─────────────────────────────►  1000ms
                                                    ↑
                                            刻意保持稳定供给
                                        否则后期充不满,难度陡然失控
```

**90 秒封顶**是刻意的:给新手足够长的"我还行"窗口,而不是无限变难把人劝退。

## 7. 怎么送到玩家手上

这部分你最熟,因为它最像后端。

```
              玩法代码
                 │  只认这一个接口
                 ▼
        ┌─── PlatformAdapter ───┐
        │  init                 │
        │  loadingStart/Stop    │  生命周期信号
        │  gameplayStart/Stop   │  (平台靠这个判断"玩家真在玩")
        │  happyTime            │
        │  showInterstitial     │  广告
        │  showRewarded → bool  │  ← 返回值就是"发不发奖"
        │  save / load          │  存档
        │  getSettings          │  平台静音开关
        └───────────────────────┘
             ▲              ▲
    CrazyGamesAdapter   WebAdapter
```

**铁律**:玩法代码里永远不许出现 `window.CrazyGames`。

这和你在 FastAPI 里"业务层不直接调云厂商 SDK,走 Provider 接口"是**同一件事**。

### 场景流转(实读代码画的)

```
  Boot ──► Menu ──┬──► Play ──► Result ──┬──► Play(再来一局)
   │              │       ▲              │
   │              │       └──────────────┘
   │              └──► Settings ──► Menu
   │
   └─ 刻意不淡出:启动瞬间屏幕本来就空的
```

### 五道门禁

```
npm run package
  ① check:boundaries  ─── 分层边界(core/ 不许 import 引擎)
  ② test              ─── 29 个单元测试
  ③ tsc --noEmit      ─── 类型检查
  ④ vite build        ─── 构建
  ⑤ build-zip 断言    ─── 体积/文件数/必须相对路径
                            ↓
                    任何一道红了,出不了包
```

> **核心哲学:约束不写在会过期的文档里,写在会 `exit 1` 的地方。**

# 心智模型

## 一句话

> **游戏 = 每秒跑 60 次的 while 循环,每次做四件事:读输入 → 算状态 → 判碰撞 → 重画。**
>
> **其余全部复杂度,都是在这四件事上加"让玩家感觉更好"。**

## 一帧里到底发生什么(这次实读了真实代码)

```
每帧(约 16.7ms):
│
├─ 0  还在玩吗?     暂停/死亡中直接 return        ← 状态机守卫
├─ 1  推进时间       state.tick(delta)             ← 连击倒计时在这走
├─ 2  读输入移动     player.update(delta)          ← 朝 followTarget 插值
├─ 3  算当前难度     difficultyAt(存活秒数)        ← 纯函数,可单测
├─ 4  生成/回收      hazards.update() motes.update()
├─ 5  擦身检测       updateGraze()                 ← 线段判定
├─ 6  更新 UI        playerRing / runTimeline / hud
└─ 7  首局引导       tutorial.update()             ← 非首局不存在,零开销

★ 碰撞不在这个列表里 —— 引擎自己跑,撞上了回调你
```

## 「5 步看懂任何 2D 游戏项目」

```
1. 找 update()      → 心脏在哪,每帧做什么
2. 找场景列表       → 有几个界面、怎么跳
3. 找数值文件       → 手感全在这(这个 demo 是 tuning.ts)
4. 找输入处理       → 玩家怎么操作
5. 找碰撞回调       → 游戏规则的核心判定
```

这五个找到,任何 2D 项目你能看懂七成。

## 关键易错点(这个 demo 全部踩过)

| 坑                     | 症状               | 为什么难查               |
| ---------------------- | ------------------ | ------------------------ |
| 忘乘 `delta`           | 高刷屏上游戏变快   | 你自己屏幕上完全正常     |
| **相机缓动名写错**     | **按一下就卡死**   | tween 里同样写法是合法的 |
| 对象池复用没重置干净   | 偶尔有东西自己消失 | 极难复现                 |
| 池化后用延时回调持引用 | 同上               | 同上                     |
| 遍历中销毁数组元素     | 偶尔漏一个         | 概率性                   |
| 场景切走没解绑全局监听 | 第二局出现两个面板 | 第一局完全正常           |

**共同点:类型检查、单元测试、构建全都抓不到。**

你昨天按空格发现的就是第二行 —— `'Sine.Out'` 在 tween 里合法,在相机效果里直接打死游戏循环。

# 后续怎么升级

## 路线一:升级玩法

```
成本 ──────────────────────────────────────────────►

改数值        换主题        加机制        换玩法
tuning.ts     theme.ts      core/+Play    几乎全重写
分钟级         小时级         天级          周级
  │             │             │             │
调难度/       换配色/       加护盾/       躲避
调手感        换文案        加 BOSS       → 推箱子
```

**第一次练手建议:改 `tuning.ts` 的数字。** 把 `followLerp` 从 `0.18` 调到 `0.35`,你会立刻感受到"跟手"和"厚重"的区别。这是理解手感最快的方式,五分钟见效。

## 路线二:升级素材

现在是**零外部素材**(贴图程序生成、音效 WebAudio 合成)。刻意的:零授权风险,包体只有 326 KB。

```
上真素材的四步:

1. 素材从哪来    Kenney(kenney.nl)—— CC0,打包下载,零心智负担
2. 代码怎么改    BootScene 的 generateTextures() → this.load.image()
3. 这时才有用    加载遮罩真正派上用场(现在零素材永远不触发)
4. 开始要管钱    体积预算变成真约束
```

**一个必须记住的数学关系:**

```
宽高各翻倍  =  面积 4 倍  =  图片体积约 4 倍

现在分辨率 1920 是"清晰"的选择 —— 零素材时这个选择免费
一旦用真图片,"清晰 vs 小包体"就是真取舍了
```

## 路线三:转其他平台 —— 这个工程最大的收益

```
                玩法代码(一行不改)
                       │
              PlatformAdapter 接口
                       │
   ┌───────────┬───────┴────┬──────────────┐
CrazyGames    Poki      itch.io    GameDistribution
  ✅已做     写个adapter  几乎白送      写个adapter
              ~100 行   (用 WebAdapter)  ~100 行
```

平台差异主要在:

|          | CrazyGames  | Poki   | itch.io |
| -------- | ----------- | ------ | ------- |
| SDK 形式 | script 标签 | npm 包 | 无      |
| 广告     | 有          | 有     | 无      |
| 云存档   | 有          | 有     | 无      |

`capabilities` 那套能力位就是为此准备的 —— **平台没有的能力,UI 自动不显示**(比如 itch.io 上"设置"页会自动多出音量开关,因为没有平台外框提供它)。

## 路线四:转 2.5D / 3D —— 这里要泼冷水

### 先分清 2.5D 的两种含义(新手常混)

```
① 伪 2.5D(等距/斜 45°)—— 本质还是 2D
   ┌──────────────┐
   │      ◇       │   贴图画成菱形,坐标还是 (x, y)
   │     ◇ ◇      │   只是渲染顺序按 y 排(下面的挡上面的)
   │    ◇ ◇ ◇     │
   └──────────────┘
   → Phaser 完全能做,工程结构几乎不动,改的是贴图和排序

② 真 2.5D(3D 场景 + 2D 玩法)
   有真 z 轴、有透视、有光照
   → Phaser 做不了,换 Three.js / Babylon.js
```

### 转 3D 能带走什么

```
┌────────────────────────┬──────────┐
│ platform/ 平台适配     │ ✅ 完整   │  它压根不知道引擎是什么
│ scripts/ 交付门禁      │ ✅ 完整   │
│ core/ 规则层           │ ✅ 完整   │  零引擎依赖,这个设计现在兑现了
│ 整套分层思路           │ ✅ 完整   │
├────────────────────────┼──────────┤
│ objects/ effects/ hud/ │ ❌ 全重写 │  Phaser API
│ 碰撞/渲染/动画的做法   │ ❌ 全重写 │  完全不同的心智模型
└────────────────────────┴──────────┘
```

**3D 新增的、2D 完全没有的概念:**

```
相机    位置 / 朝向 / 视野角     ← 2D 只有"看哪里"
光照    方向光 / 点光 / 阴影     ← 2D 直接上色
材质    金属度 / 粗糙度 / 法线   ← 2D 就是一张图
模型    网格 + 骨骼动画          ← 2D 是序列帧
深度    z 轴 + 深度排序          ← 2D 只有图层
```

> **建议:先用这个 2D demo 把"帧循环 + 手感 + 交付"吃透。3D 是另一门手艺,不是 2D 的延伸。**
>
> 而且做 3D 你会怀念现在这个 326 KB 的包 —— **一个 3D 模型就可能比它大**。

## 🟠 缺口三:没在真实设备上测过

帧率一致性、低配性能、触屏手感 —— 全是理论推断。手机、144Hz 屏、Chromebook 一个都没测。

## 🟠 缺口四:你还没自己写过一行游戏代码

**这个 demo 是我写的。读懂 ≠ 会写。**

**建议的第一个练习(约 30 分钟,不改结构):**
