# AI-first 游戏心智模型

这篇文档回答：你作为 Web/后端开发者，如何用 AI 和多 agent 理解游戏开发这件事。

本文负责：

- 你的真实角色
- AI-first 成本模型
- 游戏开发最小心智模型
- 常见认知误区

## 你的真实角色

你不是传统意义上的“游戏开发新手”。

更准确的角色是：

```
AI-first 游戏产品工程师 / 技术制片人
```

你负责：

- 选商业方向
- 定平台
- 定玩法边界
- 拆任务给 AI / agent（AI 子任务执行者）
- 验收游戏手感、性能、规则和接入
- 控制版权、平台合规和交付质量
- 对接客户或平台

AI / agent（AI 子任务执行者）负责：

- 生成玩法代码
- 生成 UI / 动效 / shader（着色器，控制画面材质和特效） / adapter（适配层，对接平台差异）
- 重构和修 bug
- 查平台文档
- 写测试和验收脚本
- 生成素材草案
- 协助改包、压缩、兼容和截图

你真正需要学的不是“每个框架所有 API”，而是下面这张图：

```
商业目标
  |
  v
渠道平台规则
  |
  v
游戏形态
  |
  v
技术栈 / 引擎
  |
  v
资产管线
  |
  v
SDK（平台开发包） / PlatformAdapter（平台适配层）
  |
  v
测试 / 上线 / 投放 / 报价
```

只要你能把需求讲清楚、把验收标准写清楚、把平台限制看明白，AI 就能把大量实现工作压下去。

## 第一性原理：这个副业真正回答什么

不要从“我要学哪个游戏引擎”开始。游戏副业本质上只有七个根本问题。

| 根本问题 | 通俗说法 | 具体答案 | 常用度 |
| --- | --- | --- | --- |
| 用户为什么玩 | 30 秒内有什么爽点 | 一个能被立即理解的核心循环 | 地基 |
| 渠道为什么要你 | 平台或客户拿它干嘛 | 提高留存、广告展示、投放转化或作品曝光 | 地基 |
| 代码跑在哪里 | 浏览器、WebView（App 内嵌网页容器）、小游戏容器还是引擎导出 | 决定渲染、包体、SDK（平台开发包）、存储、支付和审核 | 地基 |
| 素材从哪里来 | 图片、音效、模型是否合法且统一 | AI 生成、开源素材、Blender（3D 建模工具）清理、版权记录 | 地基 |
| 怎么接平台 | 广告、存档、排行榜、支付、生命周期谁管 | GameCore（游戏核心逻辑）不碰 SDK（平台开发包），全部走 PlatformAdapter（平台适配层） | 地基 |
| 怎么证明完成 | 什么叫可交付 | 真机可玩、包体合格、无报错、英文界面、可投稿/可报价 | 地基 |
| 怎么赚钱 | 钱从哪来 | 平台广告分成、Playable Ads（可试玩广告）外包、模板销售、IAP（应用内购买）、付费下载 | 地基 |

你要建立的不是“游戏开发者完整知识体系”，而是：

```
渠道判断能力
玩法切割能力
AI 任务拆解能力
平台接入验收能力
商业交付能力
```

## AI-first 成本模型

传统判断里，“没做过游戏”意味着：

- 要学引擎
- 要学动画
- 要学碰撞
- 要学状态机
- 要学打包
- 要学平台 SDK（平台给你的广告、存档、支付等接口）
- 要自己一点点调 bug

AI-first 后，成本结构变了。

```
传统成本：
学习 API + 写代码 + 调试 + 做素材 + 接平台 + 测试

AI-first 成本：
定义边界 + 拆任务 + 选平台 + 验收质量 + 修正 AI 偏差 + 商业分发
```

也就是说，代码不再是最大瓶颈。

新的瓶颈是：

- 你是否知道平台要什么
- 你是否知道游戏“好玩”的最小结构
- 你是否能判断 AI 写出来的东西有没有质量问题
- 你是否能把同一款游戏适配到不同渠道
- 你是否能拿到反馈、报价、投稿结果或收入数据

AI-first 的正确用法不是“让 AI 乱写一个游戏”，而是：

```
主 agent：维护产品规格、技术边界、验收清单
开发 agent：实现玩法、UI、动画、性能优化
平台 agent：查 SDK（平台开发包）、接广告、接 IAP（应用内购买）、改打包
素材 agent：生成和整理图片、音效、3D 模型
测试 agent：做移动端、桌面端、包体、FPS（每秒帧数）、异常流验收
审查 agent：检查版权、平台规则、质量和安全风险
```

你不需要先把 Phaser、Three.js、Unity、Godot、Cocos 都学完。

你需要先能回答：

```
这个游戏要投到哪里？
这个渠道靠什么变现？
它支持什么 SDK（平台开发包）？
它禁止什么？
它接受什么格式？
它的用户在哪些设备上玩？
我怎么知道它有商业信号？
```

## 游戏开发的最小心智模型

你有 Python / FastAPI / Django / Flask / 数据库经验，可以这样迁移理解。

Web 后端通常是：

```
Request -> Router -> Service -> DB -> Response
```

游戏客户端通常是：

```
Input（输入）
  -> Update（更新）
  -> Physics/Rules（物理/规则）
  -> Render（渲染）
  -> Audio（音频）
  -> Next Frame（下一帧）
```

后端是“请求响应模型”，游戏是“帧循环模型”。

关键区别：

| 后端请求模型 | 游戏帧循环模型 |
| --- | --- |
| 一次请求进来，处理完返回响应 | 游戏启动后，每一帧都重复处理 |
| 核心问题是“这次请求返回什么” | 核心问题是“下一帧世界变成什么样” |
| 数据通常来自 HTTP、DB、缓存、队列 | 数据通常来自玩家输入、上一帧状态、时间流逝 |
| Router / Service / DB 是主线 | Input（输入）/ Update（更新）/ Render（渲染）是主线 |
| 响应发出后这次链路结束 | 下一帧马上继续，直到暂停或结束 |

一帧可以理解为游戏世界的一次“心跳”。30 FPS 表示每秒心跳 30 次，60 FPS 表示每秒心跳 60 次。玩家看到的流畅感，就是很多帧连续发生的结果。

每一步的意思：

| 英文术语 | 中文理解 | 游戏里具体发生什么 |
| --- | --- | --- |
| `Input` | 输入 | 读取触摸、鼠标、键盘、手柄，比如玩家按下跳跃或拖动挡板 |
| `Update` | 更新 | 根据时间推进玩家、敌人、分数、倒计时、动画状态 |
| `Physics` | 物理 | 处理速度、重力、碰撞、反弹、边界，简单游戏可以很轻 |
| `Rules` | 规则 | 判断得分、扣血、胜利、失败、关卡是否结束 |
| `Render` | 渲染 | 把当前状态画到 Canvas（浏览器 2D 画布）、WebGL（浏览器图形渲染能力）、DOM 或引擎画布上 |
| `Audio` | 音频 | 播放点击、得分、碰撞、失败、奖励等反馈 |
| `Next Frame` | 下一帧 | 进入下一次刷新，继续重复这一套流程 |

注意：这里的 `Render` 不等于 React 组件渲染。游戏里的渲染更像“把当前游戏世界画成这一张画面”，下一帧再画下一张。

### 游戏循环

游戏不是页面静态展示，而是每秒不断刷新状态。

```
while game is running:
    readInput()
    updateWorld(deltaTime)
    resolveCollision()
    renderFrame()
    playAudio()
```

浏览器里通常是：

```
function loop(time) {
  const dt = time - lastTime;
  update(dt);
  render();
  requestAnimationFrame(loop);
}

requestAnimationFrame(loop);
```

你需要关注：

- `state`：玩家、敌人、分数、关卡、倒计时
- `input`：触摸、鼠标、键盘、手柄
- `update`：移动、碰撞、胜负判断
- `render`：Canvas（2D 画布） / WebGL（浏览器图形渲染） / DOM / CSS
- `audio`：点击后解锁、音效、背景音乐
- `lifecycle`：暂停、恢复、切后台、广告前后

### 游戏的基本模块

```
GameCore
  - 规则
  - 状态
  - 关卡
  - 分数
  - 胜负

RenderRuntime
  - Canvas 2D
  - WebGL
  - Three.js
  - Phaser
  - PixiJS
  - Cocos

InputSystem
  - touch
  - pointer
  - keyboard
  - gesture

AssetPipeline
  - image
  - sprite
  - atlas
  - audio
  - font
  - glTF / GLB

PlatformAdapter
  - ads
  - analytics
  - storage
  - leaderboard
  - share
  - payment / IAP
  - lifecycle
  - consent / privacy

BuildPipeline
  - dev
  - preview
  - zip
  - minify
  - texture compress
  - platform package
```

这张模块图的读法：

- `GameCore`（游戏核心逻辑）：负责规则、状态、分数和胜负。
- `RenderRuntime`（渲染运行时）：负责把游戏画出来，可以是 Canvas（浏览器 2D 画布）、WebGL（浏览器图形渲染）、Phaser、Three.js 等。
- `InputSystem`（输入系统）：负责触摸、鼠标、键盘和手势。
- `AssetPipeline` 是资产管线，负责图片、音频、字体、3D 模型的生产、压缩和导入。
- `PlatformAdapter`（平台适配层）：负责广告、存档、排行榜、支付、分享、生命周期。
- `BuildPipeline` 是构建管线，负责把同一套代码打包成 Web、平台包、广告包等不同产物。

### 数据库和后端什么时候需要

很多第一版小游戏不需要数据库。

优先级通常是：

```
第一阶段：localStorage（浏览器本地键值存储） / IndexedDB（浏览器本地数据库）
第二阶段：平台排行榜 / 平台存档
第三阶段：自建后端
第四阶段：账号系统 / 支付 / 反作弊 / 数据分析
```

你熟悉的 FastAPI / Django 适合放在第三阶段以后：

- 排行榜
- 用户进度
- 活动配置
- A/B 测试
- 远程关卡配置
- 支付验签
- 反作弊
- 运营数据

第一周不要把后端当核心，除非目标平台要求服务端验签，比如 Telegram / Discord 的付费或身份场景。

## 常见误区

### 误区 1：先系统学完游戏引擎

不需要。

你要先知道渠道要什么，再围绕目标学习最小必要知识。

### 误区 2：AI 能解决全部问题

AI 能降低开发成本，但不能替你确认：

- 平台规则
- 版权
- 商业需求
- 用户反馈
- 真机性能
- 客户付款

### 误区 3：Three.js 不是游戏框架，所以不能用

不准确。

Three.js 确实不是完整游戏框架，但 AI-first 下它非常适合：

- 轻 3D 游戏
- 3D 展示互动
- playable ads
- 视觉差异化 Demo

关键不是它是不是“完整引擎”，而是你能不能把游戏范围控制在：

```
AI 能生成
你能验收
手机能跑
平台能接
客户能理解
```

### 误区 4：上线平台就能赚钱

不准确。

平台上传只是开始。收入取决于：

- 审核通过
- 获得流量
- 留存
- 时长
- 广告填充
- 地区
- 玩法质量
- 迭代能力

### 误区 5：低价单没有价值

也不准确。

低价单可以用来：

- 练交付
- 拿真实需求
- 做案例
- 验证流程

但不能长期停留在低价单。你的目标应该是把低价单沉淀成：

```
模板
作品集
报价包
平台适配经验
客户案例
```

## AI-first 的边界

事实：

- AI 可以显著降低代码生成、样式调整、脚本编写、素材草案、文档和测试清单成本。
- 平台规则、收款条件、审核要求、广告 SDK（广告接口开发包）和包体限制会变化，不能只靠模型记忆。
- 游戏手感、移动端性能、素材版权、客户付款和平台流量必须用真实反馈验证。

推断：

- 在你有开发能力、Codex / Claude 会员和多 agent 工作流的前提下，一周内跑通“可玩链接 + 样片 + 投稿/报价 + 反馈通道”是现实的。
- 一周内稳定赚钱不是纯开发问题，取决于客户来源、平台审核、报价能力和响应速度。

因此你要用 AI 抢时间，但不能用 AI 代替验收。

## 人必须亲自验收什么

AI 写完代码不等于游戏完成。你必须亲自验收这些东西：

| 验收项 | 为什么不能完全交给 AI |
| --- | --- |
| 手感 | AI 能写逻辑，但不知道拖动、点击、碰撞反馈是否舒服 |
| 难度曲线 | AI 容易让游戏太简单、太难或没有成长感 |
| 移动端 | 模拟器正常不代表真机触摸、音频、横竖屏、发热正常 |
| 首屏卖点 | 客户和平台通常几十秒内判断值不值得继续看 |
| 平台 SDK（平台开发包） | 调用时机错了可能审核不过或无法计费 |
| 素材版权 | AI 不会自动替你证明素材可商用 |
| 商业交付 | 报价、源码、买断、独占、修改次数必须你自己拍板 |

AI 产物常见失败样例：

- 玩法能跑，但没有爽点
- UI 看起来完整，但手机上按钮太小
- 动画很多，但关键反馈不明显
- 代码能 build，但一接广告就状态乱
- 桌面能玩，iPhone Safari 音频不触发
- 资产好看，但风格不统一或来源不清
- demo 能展示，但没有截图、视频、报价包和投稿材料

你的角色不是替 AI 写每一行代码，而是把这些失败提前写成验收标准。
